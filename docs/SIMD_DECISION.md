# SIMD decision record — is AVX2 faster than scalar for Zentropy?

> **Question.** The predictor's hot loop is a per-bit sequence of ~30 hashed
> memory accesses. Would AVX2 intrinsics beat scalar?
>
> **Answer: no, not for this loop.** Measured here, and consistent with the
> published evidence. The scored path stays scalar. This file exists so the
> question is not re-litigated from intuition.
>
> Reproduce: `rustc -O -C target-cpu=native tools/simd_bench.rs -o /tmp/simd_bench && /tmp/simd_bench`

## 1. Why the prior is "scalar"

* **AVX2 gather is a pretend instruction.** `vpgatherdd` decodes to eight
  independent micro-loads; the gather unit is the bottleneck and throughput is
  roughly one element per cycle at best. For latency-bound random access it does
  not beat scalar loads — one measurement reports "~24 ns regardless of pattern;
  it barely beats scalar" (serenedb, 2026), and johnnysswlab's AVX2-gather study
  finds the vector/scalar ratio *degrades* as the working set leaves cache.
* **AVX2 has no scatter.** Our loop is read-modify-write: even a perfect gather
  must still perform eight scalar stores, so the update cannot be vectorised
  end-to-end.
* **Compilers often win anyway.** GCC/Clang default to 256-bit vectors on Intel
  targets, and hand-written intrinsics "can sometimes result in worse
  performance relative to the code generated by the compiler" (AVX-512 ISA
  article, §Performance).

## 2. What we measured

`tools/simd_bench.rs`, `-O -C target-cpu=native`, AMD Ryzen 7 9800X3D (Zen 5).
Two runs, because run-to-run variance on a shared workstation is real:

| pattern | scalar | AVX2 | prefetch |
|---|---|---|---|
| **A** random table lookup+update (64 MiB table, 8 lookups/round) | 5.19 / 5.94 ns | 7.82 / 7.04 ns | 4.83 / 6.63 ns |
| **B** mixer dot, `i16` inputs (64 inputs) | 8.245 ns | 5.441 ns (**1.52×**) | — |
| **B'** mixer dot, `i32` 16.16 — *the real mixer's types* | 9.724 ns | 8.831 ns (1.10×) | — |

Readings:

* **A is the dominant cost, and AVX2 loses it**: gather is **1.19–1.51× slower**
  than scalar. That alone settles the question for the expert tables.
* **B is the one place AVX2 wins**, but the real mixer uses `i32` 16.16 weights
  and stretched `i32` inputs, i.e. row **B′ — only 1.10×** — and the dot product
  is one step of several in the mixer (weight selection, `stretch`, update), and
  the mixer is a minority of total runtime. A 1.10× on a minority component is
  worth low single-digit percent overall, and it would cost: an `unsafe` module
  (against `#![forbid(unsafe_code)]`), runtime CPU dispatch, a second code path
  to keep bit-exact, and a portability risk on a judge machine that "may change
  without notice".
* Software prefetch was **+7%** in one run and **−12%** in the other: below the
  noise floor on this machine, so it is not adopted either.

## 3. Decision

| proposal | verdict | reason |
|---|---|---|
| AVX2 gather for context tables | **REJECTED** | measured 1.19–1.51× *slower*; and no scatter makes the update scalar regardless |
| AVX2 for the mixer dot | **REJECTED** (for now) | real types give 1.10×; unsafe + dispatch + dual code path is not repaid by low single digits on a minority component |
| software prefetch in the table path | **REJECTED** | within run-to-run noise |
| SIMD in transform stages (reorder sort, hoisting, tokenisation) | **OPEN** | those are contiguous/arithmetic-dominated, unlike the predictor; they are also only ~1–3% of a pass, so the ceiling is small |

The consequence is strategic rather than local: **the throughput lever for
Zentropy is not SIMD.** The predictor is latency-bound on hashed table accesses,
so the wins available are (a) parallelism *across* independent work — candidates,
blocks — never within one sequential pass, (b) not re-paying for work already
done (the parent-skip in `eval`), and (c) cache/layout and algorithmic work on
the tables themselves. Anything that claims a big win from vectorising the
predictor should be expected to be wrong until measured.

## 4. Scope note

This record answers the question for *this* loop on *this* microarchitecture. If
a future mechanism adds a contiguous and dominant inner loop (an interleaved
multi-lane entropy coder, a histogram-heavy transform), the measurement should be
redone for that loop specifically — the test file is committed so it can be
adapted rather than rewritten.
